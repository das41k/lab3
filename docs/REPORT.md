# Отчёт по лабораторной работе № 3

## Защищённый обмен данными: симметричное шифрование и управление ключами

### 1. Цель работы

Получить практические навыки применения симметричной криптографии для
защиты данных, передаваемых между клиентом и сервером по TCP. В ходе работы
требовалось изучить принципы AES-GCM, назначение ключа и nonce, реализовать
безопасную генерацию ключа, шифрование/расшифрование JSON-сообщений,
проверку authentication tag, обнаружить изменение зашифрованного сообщения
и проанализировать типичные ошибки управления ключами.

### 2. Индивидуальный вариант

Банковская система: запросы `HELLO`, `PING`, `ACCOUNT_GET`, `TRANSFER`,
`SLOW_TEST`; ответы с балансом и результатом перевода. Протокол разработан
в ЛР2, в ЛР3 добавлен защищённый транспорт.

### 3. Исходный протокол ЛР2

Клиент и сервер обменивались JSON-объектами, по одному на строку (`\n`).
Запрос содержал `version`, `request_id`, `timestamp`, `type`, `payload`.
Ответ — `request_id`, `status`, `payload` или `error` с кодом.

Особенности ЛР2, сохранённые в ЛР3:

* версия протокола `1.0` и проверка `UNSUPPORTED_VERSION`;
* `request_id` (UUID) и идемпотентность `TRANSFER`: повтор с тем же
  `request_id` не списывает деньги повторно;
* коды ошибок `INVALID_REQUEST`, `INVALID_DATA`, `RESOURCE_NOT_FOUND`,
  `INTERNAL_ERROR`;
* таймаут и повторная отправка запроса на клиенте;
* журналирование метаданных запроса.

Недостаток ЛР2: JSON передавался открытым текстом, поэтому прикладные
данные (номера счетов, суммы) были видны при анализе трафика.

### 4. Выбор криптографического алгоритма

| Параметр | Значение |
|---|---|
| Алгоритм | AES-256-GCM (AEAD) |
| Библиотека | `cryptography` (`AESGCM`) — промышленная реализация |
| Длина ключа | 256 бит (32 байта) |
| Размер nonce | 96 бит (12 байт) |
| Размер authentication tag | 128 бит (16 байт) |
| Кодирование | base64 для JSON-конверта |

AES-GCM выбран потому, что он одновременно обеспечивает конфиденциальность
и контроль целостности/аутентичности (AEAD). Собственная реализация
криптоалгоритма не использовалась. `cryptography` — стандартная для Python
промышленная библиотека, аналог Java Cryptography API, применённого в
методических указаниях.

### 5. Архитектура защищённого взаимодействия

```
CLIENT
  Application (Request)
        │
        ▼
  BankingProtocol.seal()
        │  AES-256-GCM: nonce + ciphertext + tag
        ▼
  MessageFramer (JSON + '\n')
        │
        ▼
  TCP
        │
        ▼
  MessageFramer.recv()
        │
        ▼
  BankingProtocol.open()
        │  проверка tag и AAD
        ▼
  OrderService.handle() → Response
        │
        ▼
  BankingProtocol.seal() → TCP → CLIENT → open() → Response
```

Разделение ответственности:

* `crypto/` — шифрование, расшифрование, ключи, nonce;
* `protocol/` — структуры сообщений и формат конверта;
* `service/` — банковская бизнес-логика;
* `client/`, `server/` — сеть и оркестрация.

Протокол переписан в виде классов данных: `ProtocolMessage` (база),
`Request`, `Response`, `EncryptedMessage`, а операции выполняет
`BankingProtocol`. Модульные функции `make_request`/`serialize_message`
из ЛР2 больше не используются.

### 6. Формат защищённого сообщения

Внутри шифруется обычный JSON ЛР2 (UTF-8):

```json
{
  "version": "1.0",
  "request_id": "8f0c...",
  "timestamp": "2026-11-17T10:30:00+00:00",
  "type": "TRANSFER",
  "payload": {"from": "ACC-1001", "to": "ACC-1002", "amount": 500.0}
}
```

По сети передаётся конверт:

```json
{
  "version": "1.0",
  "request_id": "8f0c...",
  "kind": "REQUEST",
  "key_id": "key-2026-11",
  "nonce": "<base64, 12 байт>",
  "ciphertext": "<base64>",
  "tag": "<base64, 16 байт>"
}
```

* `version` — версия протокола;
* `request_id` — идентификатор запроса/ответа;
* `kind` — `REQUEST` или `RESPONSE` (конверт один для обеих сторон);
* `key_id` — идентификатор версии ключа (нужен для ротации);
* `nonce` — не секретен, передаётся вместе с ciphertext;
* `ciphertext` — зашифрованный JSON;
* `tag` — authentication tag GCM.

AAD формируется из `version`, `kind`, `request_id`, `key_id` с явным
кодированием длин полей. Благодаря этому изменение открытых метаданных
приводит к ошибке аутентификации. После расшифрования проверяется, что
`request_id` и `version` внутри сообщения совпадают с конвертом.

### 7. Управление ключом

* **Генерация:** `scripts/generate_key.py` использует `os.urandom(32)`,
  то есть криптографически стойкий генератор ОС. Ключ записывается в
  локальный `.env` в base64; в консоль выводится только отпечаток.
* **Хранение:** `.env` и `keys/keyring.json` исключены из Git
  (`.gitignore`). В репозитории находится только `.env.example` с
  заглушкой. Ключ не хранится в исходном коде и не пишется в журналы.
* **Получение:** pydantic-settings читает `APP_ENCRYPTION_KEY` и
  `APP_KEY_ID`; `KeyManager` проверяет длину ключа (32 байта) и
  предоставляет его криптомодулю. `SecretStr` не раскрывает значение
  в `repr()`.
* **Ротация:** `scripts/rotate_key.py` генерирует новый ключ с новым
  `key_id`, сохраняет старый в `keys/keyring.json` и обновляет `.env`.
  Сервер выбирает ключ по `key_id` из конверта, поэтому старые сообщения
  можно расшифровать, а новые защищаются новым ключом. Код при этом не
  меняется.
* **Журналирование:** фиксируются `key_id`, короткий SHA-256-отпечаток
  ключа, отпечаток nonce, `request_id`, тип и статус. Ключ и base64-ключ
  в журналы не попадают.

Эксперименты (`uv run python scripts/experiments.py`):

1. **Обычный обмен.** `HELLO` → `SUCCESS`; запрос 377 байт, ответ 370 байт
   (значения для запуска на тестовом стенде; зависят от длины `request_id`).
2. **Изменение ciphertext.** Сервер вернул `status=ERROR`,
   `code=AUTH_FAILED`; соединение осталось рабочим.
3. **Изменение nonce.** `AUTH_FAILED` — расшифрование невозможно.
4. **Неправильный ключ.** Сервер отклонил запрос; клиент с другим ключом
   не смог расшифровать даже ответ сервера (`AuthenticationError`).
5. **Повторное использование nonce (replay).** Первая отправка `SUCCESS`,
   повторная — `ERROR/AUTH_FAILED`.
6. **Уникальность nonce.** 100 сообщений → 100 уникальных nonce.
7. **Анализ трафика.** Открытый JSON ЛР2 — 210 байт; конверт ЛР3 — 446
   байт; накладные расходы +236 байт. В конверте не найдены строки
   `ACC-1001`, `ACC-1002`, `500.0`, `TRANSFER`, `payload`.
   Видны только `version`, `request_id`, `kind`, `key_id`, `nonce`,
   `ciphertext`, `tag`.

### 9. Анализ сетевого трафика

В ЛР2 по TCP передавался читаемый JSON: были видны тип операции, счета и
суммы. В ЛР3 полезная нагрузка заменена на base64-шифротекст; прикладные
данные не видны. Наблюдаемые метаданные:

* версия протокола и `request_id`;
* направление сообщения (`kind`);
* идентификатор версии ключа `key_id`;
* длина ciphertext и фиксированные размеры nonce/tag.

Размер сообщения вырос примерно на 100–240 байт из-за nonce, tag,
base64-кодирования и метаданных. Это приемлемая плата за AEAD-защиту.
Паттерн трафика (частота и размеры сообщений) по-прежнему наблюдаем — это
одно из нерешённых ограничений.

### 10. Анализ типичных ошибок

1. **Собственный алгоритм шифрования.** Криптоалгоритмы требуют
   многолетнего анализа; самодельная схема почти наверняка содержит
   неизвестные уязвимости. В работе используется проверенный AES-GCM.
2. **Ключ в исходном коде.** Секрет попадает в Git и историю коммитов,
   доступен всем разработчикам. Ключ вынесен в `.env`, исключённый из Git.
3. **Фиксированный nonce.** При AES-GCM повтор nonce с одним ключом
   компрометирует конфиденциальность и аутентичность. Nonce генерируется
   заново для каждого сообщения; повтор обнаруживается `NonceTracker`.
4. **Передача ключа по обычному TCP.** Ключ может быть перехвачен.
   В работе ключ предварительно распределён вне сети; передача ключа по
   прикладному TCP не реализуется.
5. **Ключ в журнале.** Журналы доступны шире, чем сам секрет. Логируются
   только `key_id` и несекретные отпечатки.
6. **Один ключ без замены.** Компрометация долговременного ключа
   затрагивает все данные. Реализована ротация с сохранением старых
   ключей только для расшифрования и с указанием `key_id` в конверте.

Дополнительно: нельзя доверять открытым полям конверта — `version`,
`request_id`, `kind`, `key_id` включены в AAD, поэтому их изменение
обнаруживается до обработки запроса.

### 11. Вывод

В результате ЛР3 протокол ЛР2 получил защищённый вариант:

* прикладные JSON-сообщения шифруются AES-256-GCM;
* для каждого сообщения генерируется новый случайный nonce;
* целостность и аутентичность проверяются по 128-битному tag;
* изменение ciphertext, nonce, tag, AAD или использование другого ключа
  приводит к отказу;
* ключ не хранится в коде и не попадает в журналы; поддерживается ротация;
* сервер отклоняет replay и слишком большие сообщения;
* идемпотентность и обработка ошибок ЛР2 сохранены.

Остаются нерешёнными задачи безопасного первоначального распределения
ключа, взаимной аутентификации сторон, forward secrecy и защита от
трафика-анализа. Эти вопросы относятся к асимметричной криптографии,
обмену ключами и TLS (следующие лабораторные работы).

Вывод: безопасность протокола определяется не только выбором алгоритма,
но и корректной генерацией/хранением ключей, уникальностью nonce,
аутентификацией метаданных и дисциплиной журналирования.
